# Finite obligation and ledger contracts

The typed contracts live in `operational_quality.control_coverage`. A register selects 1–50 unique synthetic obligations within seven days, with an approved register hash before the window start. Each obligation fixes control ID, version, opaque scope digest, earliest start, due time and owner role. Duplicate semantic obligations are rejected even if assigned different IDs. No cron/recurrence expansion, business-calendar calculation or schedule creation exists. The entire selected register is the denominator; unknowns and approved skips remain visible as distinct states.

Mock ledgers accept at most 200 runs and 200 skips, with exact obligation IDs, counts, availability/truncation, start/end coverage and bounded clock uncertainty for both sources. Missing/partial/stale feeds, unknown identities or invalid manifests block interpretation. Incomplete inventory of skips cannot establish an unexcused missed run. Counts/completeness are assertions, not proof of real-world completeness. Input JSON is bounded to one MB per file, and combined output to one MB.

Run records contain strict demo IDs, matching control/version/scope, aware start/finish/recorded times, success/failed labels and an optional explicit previous-run ID. No arbitrary messages or patient fields are accepted. Invalid payloads are quarantined without raw content; duplicate or cross-obligation IDs/links block all affected obligations. Source-role and scope mapping are supplied assumptions, not authenticated destinations or verified control logic. A scope hash does not validate the underlying selection.

Retries must form one explicit ordered non-overlapping chain, beginning without a predecessor. Failed attempts followed by a linked success can produce a recorded-success state, with all attempts retained. A retry after recorded success is unknown because this contract has no evidence mechanism for invalidating a prior success; latest timestamp alone cannot discard it. Branching, missing, overlapping or cross-obligation retry links are unknown.

Run timestamps must fit the certain obligation/audit window. Deadline classification accounts for clock uncertainty: success entirely beyond due plus grace is late; overlapping the threshold is unknown. An absent execution is reported only when both ledger cutoffs minus uncertainty exceed due plus grace. A failed run is a recorded result, not proof of faulty business outcomes. In-progress runs without completed times are unknown, not failures.

A skip must be individually approved before earliest start, bind the obligation digest and have a valid exact approval quote of its own content hash. Revoked, altered, multiple or unresolved skips yield unknown. Skip plus execution is a conflict; no automatic latest-state resolution. Rejected skip quotes are omitted from output. Valid quoted provenance is still untrusted data and does not authenticate authority. Approval and skip records may contain fictional prose only; synthetic IDs and redaction are not comprehensive sensitive-data detection.

Reports retain record IDs, typed run histories, safe skip content, verified quote provenance, counts, source coverage, uncertainty reasons and a canonical digest. No live integration is claimed. Reuses shared strict models, timestamps, evidence hashes/quote checks, redaction, bounded input and private exclusive output. No vendor connector or query engine was introduced; existing read-only clients are not called by this mock-only profile.

A recorded success is not evidence of control effectiveness, error reduction, accurate underlying checks or patient safety. Human oversight is mandatory. The CLI has no model, source-write, scheduling, notification or execution path. Host instructions constrain interpretation but cannot remove permissions from a separately privileged host. This skill makes no claims about any real employer's workflow or compliance requirements.
