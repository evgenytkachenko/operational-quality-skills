# Administrative metadata contract and limits

Authoritative schemas are in `operational_quality.referral`. Scope is 1–20 distinct `REF-DEMO-nnn` case IDs over at most seven days, at most 1,000 events and a configured output-byte budget. JSON files are bounded by the shared one-MB reader. One case means exactly one immutable submitted packet revision. Resubmissions/reopened work require a separately selected case; cross-case matching or choosing the latest revision is unsupported. No patient identity exists in the schema.

A submission lists zero to three unique administrative document categories with positive version numbers and SHA-256-shaped fingerprints. A receiver receipt carries exactly one metadata item and explicitly links its submission. A receiver acknowledgment and cancellation link the same case/revision submission but contain no documents. All records require aware occurrence and ingestion times. Source-qualified IDs, demo cases and fixed document enums prevent arbitrary document text. Extra fields are quarantined without copying raw payloads. Synthetic markers do not prove absence of sensitive data; approval text must also be fictional.

Both sender and receiver manifests declare exact case scope, count, available/truncated/offline status, complete-through watermark and clock uncertainty. Partial, unavailable, delayed or offline feeds suppress interpretation. Duplicate source IDs, ambiguous case/revision mappings, missing times, unresolved/cross-case links and overlapping order intervals yield unknown. Cross-case links block both affected cases. Multiple submissions or revisions are unknown, never silently merged. Ambiguous data is not evidence of administrative fault.

Configured policy specifies required metadata categories and delivery/acknowledgment seconds. An exact quote and canonical policy hash bind an approved decision before scope start. Local applicability and authenticity require human review. Missing listed metadata is a checklist observation; receipt/acknowledgment absence is evaluated only after the elapsed threshold using the earliest feed watermark minus clock uncertainty. These are wall-clock thresholds, not working-calendar calculations.

Receiving metadata is compared to the selected submission by category, version and fingerprint. Unexpected categories or mismatches are conflicts, not proof of invalid clinical documents. Repeated identical metadata receipts with distinct record IDs do not double-count documents; conflicting repeats remain visible. Acknowledgment never clears a missing receipt. Cancellation suppresses pending checklist/delivery/acknowledgment findings but preserves observed metadata conflicts. Multiple cancellations or activity after cancellation yield unknown; start a separately scoped case for a later revision.

Fingerprints are supplied metadata, not recomputed or validated against documents. Source roles, receiver destination and case mapping are assumed, not authenticated. The profile cannot prove the correct provider received a document, that consent is valid, or that an actual referral is clinically/administratively sufficient. No document contents, urgency assessment, patient matching, scheduling, coverage or treatment decision is supported. No FHIR or other standards-compliance claim is made.

The report preserves normalized timelines, original mock refs, policy/approval provenance, feed coverage, quarantine reasons and a report hash. It does not authenticate records or supply live source URLs. Unobserved means not in available source-asserted coverage, never proof of nonperformance.

Reuses existing strict models, timestamp checks, redaction, canonical hashing, quote binding, bounded input and private exclusive output. Existing Datadog/PostgreSQL integrations are not invoked; no new medical connector is implemented or claimed verified. The CLI has no live, model, scheduling or production-write path. Host instructions constrain interpretation but cannot remove powers from a separately privileged host; all outcomes require human review.
